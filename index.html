What changes in Version 2.0

The central change is source-language freedom. Choose the language written in the saved Delphi project, then create separate, reviewable catalogs for the target languages you select.

  1. Start with the original app language. A German-authored project can be translated into French or Dutch without treating English as the source.
  2. Add several languages in one run. Scan once, select multiple targets, and keep a separate catalog for each source–target pair.
  3. Review one language at a time. Save corrections as you move through the batch; review can finish without exporting anything.
  4. Export deliberately. Validate the selected catalogs first, then choose whether to deploy the passing language packs.

A development tool, not an EXE translator

Localization stays inside the development process.

Run the Studio while forms, resources, messages, and layouts can still be examined in Delphi. Tell it the language actually present in the saved project. Rescan as the application changes, preserve translations that still match, and send only eligible unresolved text to the provider.

Machine translation can be very useful, but it cannot guarantee perfect wording or layout. The developer remains responsible for terminology, dynamic messages, custom controls, right-to-left behavior, and final visual review.

Translation with application context

Short interface words need more than a dictionary.

“Play,” “Close,” “Schedule,” and “Enable” can mean different things in different applications. The Studio adds proper context, control roles, surrounding evidence, terminology, and review status with each entry.

  • Preserves approved and reviewed work during later scans
  • Protects Delphi placeholders, accelerators, identifiers, and markup
  • Uses project glossary and translation-memory evidence
  • Separates machine drafts from human review and approval

Designer-owned integration

Normal Delphi components. Offline application runtime.

Place one framework-appropriate language manager and one connected selector on the primary form. Their published properties remain visible in Object Inspector. The finished app reads compatible packs from its local Localization\Languages folder; it does not contact DeepL or Google when users switch languages.

Source stays readableThe recommended workflow does not rewrite Pascal, DFM, FMX, DPR, or DPROJ source.
Switching is reversibleThe runtime restores the designer baseline before applying the next language.
Layout is language-awareLTR, RTL, wrapping, intelligent hyphenation, and reviewed layout rules are applied conservatively.

Your feedback matters

Help us make Delphi App Translation Studio better.

Tell us what worked, what did not work, and what could be clearer. Errors that are not reported cannot be investigated or corrected, and the application cannot continue to improve without feedback from developers using it in real projects.

Please report translation problems, right-to-left display issues, unexpected program behavior, component or package problems, documentation questions, and anything that made the workflow confusing. Even a small observation can identify an improvement that benefits every user.

When reporting an issue, please include the Delphi framework, target platform, selected language, screen or workflow involved, and the steps needed to reproduce the problem. Screenshots are helpful, but please remove API keys, private source code, personal information, and other sensitive material before submitting them.
